- HA is reached at HA_URL (LAN) with Authorization: Bearer HA_TOKEN (long-lived token). HA_TOKEN is user-provided via .env; never print it, never commit it. API_TOKEN is a DIFFERENT token: the key the frontend sends to this API (gate in src/shared/guards/apiKey.ts, Authorization: Bearer).
- Control only HA domains in the allowlist (light, switch, climate, cover, fan, media_player, scene, script); anything else -> typed ApiError (not allowed).
- Template envelope: data is always an array; use route() + ApiError subclasses. Model/Repository layer is DB-bound and unused here; HA access goes through a dedicated client module, not Repository.
- Bruno tests run against a live API that needs a reachable HA. Until a mock/real HA is available in CI, tests hit the real homelab HA on LAN (read-only calls preferred; control tests only on a dedicated test entity).
- TOKEN LOCATION: the user keeps the HA long-lived token as HA_TOKEN in F:\proyectos\home-control\.env (parent folder, outside every repo, never committed). Backend reads HA_TOKEN: copy it to home-control-backend/.env for local dev and to the Dokploy env of the backend app for deploy. NEVER put it in the frontend (Vite would bundle VITE_* vars), docs repo or Electron. Do not print it.
- TOKENS: API_TOKEN = shared key the frontend (web build and Electron) sends to THIS API as Authorization: Bearer <API_TOKEN>; HA_TOKEN = long-lived token THIS API uses against Home Assistant. Both live in F:\proyectos\home-control\.env. Backend .env gets both; frontend only gets API_TOKEN (as VITE_API_TOKEN); HA_TOKEN never leaves the backend.
- Bruno CLI pinned to @usebruno/cli 2.15.1 (devDependency). 2.x runs only from the collection root (no folder arg) and 4.x dropped --recursive; test.cjs runs 'run --env local -r' with cwd tests/bruno and the repo .env merged into env so {{process.env.API_TOKEN}} resolves. The API runs on API_PORT from .env (3003 here).
- SCOPE EXCEPTION (008 entity-aliases): project.md says no own DB/persistence. Approved exception: ONE tiny JSON file store for user entity aliases only (ALIASES_FILE, default /data/aliases.json, Docker volume, atomic tmp+rename, <=2000 aliases, alias<=80 chars). No database, no other persisted state; anything more needs a new decision. Entities/areas/stream never carry the alias (client merges).
- SCOPE EXCEPTION (010 cover-calibration): second tiny JSON file store, ONLY for cover open/close calibrations (CALIBRATIONS_FILE, default /data/calibrations.json, same /data volume as aliases, atomic tmp+rename, <=200 covers). Still no database and no other persisted state; anything more needs a new decision.
- 011 known gaps: PUT /api/calibrations during a running move may be overwritten by that move's timer; two concurrent cover-percent requests for same cover have no lock.
- SCOPE EXCEPTION (012 alert-rules): third tiny JSON file store, ONLY for notification alert rules (ALERT_RULES_FILE, default /data/alert-rules.json, same /data volume as aliases and calibrations, atomic tmp+rename via shared JsonFileStore, <=500 rules, one rule per entity+trigger type+value). Rules are stored only; evaluation runs in the frontend from the SSE stream. Still no database and no other persisted state; anything more needs a new decision.
